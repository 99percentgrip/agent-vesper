# v0.23.3 — Bridge ships in release binaries with native Settings activation

## Objective

v0.23.1 advertised Vesper Bridge as "experimental, default-off" but the
release artifacts contained **zero Bridge code**: `release.yml` compiled
only `docker,swarm` features. Additionally, even in a bridge-enabled
build the only documented activation path was hand-editing
`.agent-vesper/bridge-settings.json` — a violation of the house rule
that feature activation belongs in native Settings. v0.23.3 fixes both.

## Defects fixed

1. **Release feature matrix omission (shipping defect).**
   `.github/workflows/release.yml` line 157 now builds with
   `agent-vesper-acp/bridge,agent-vesper-tui/bridge`. Verified the local
   release build contains `bridge_connect` in both binaries and the
   `Settings › Bridge` panel string in the TUI (byte-grep receipts
   against `target/release/`).

2. **No native activation surface (house-rule violation).**
   - TUI: `/settings` menu gains `Bridge · application control
     (experimental)` exactly when the feature is compiled in
     (`cfg!`-tested); the panel is a single draft with Save changes /
     Discard changes semantics, themed, persisted with the other
     Settings choices in one transaction.
   - ACP: `/settings bridge <enabled on|off|save|cancel|status>` text
     controls with swarm-like draft semantics, per-session draft state
     (`BridgeControls`), workspace-switch draft reset.
   - `/bridge status` disabled text now points to `/settings → Bridge`
     instead of printing a JSON snippet. A regression test pins that the
     disabled answer never instructs hand-editing a settings file.

3. **Vacuous AT-01 enabled-pass (test defect found by the text change).**
   The ACP OS-observation test asserted `status.contains("enabled")` —
   which the OLD disabled text satisfied, because that text embedded the
   literal JSON snippet `{"enabled":true}`. Removing the snippet made the
   assertion fail, exposing that the host had never actually read an
   enabled settings file in that test. Root causes fixed:
   - `spawn_binary` never set a `current_dir`, so the child inherited the
     *test runner's* cwd; the harness now pins the child cwd to the
     isolated temp root (hermetic for every user of this harness).
   - The test wrote the settings file to a stray tempdir unrelated to
     where the host resolves workspace settings; it now writes to the
     isolated root the host actually reads.
   - The enabled pass now genuinely reports `Bridge: enabled`.
